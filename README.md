# Hotelog API

## Описание

**Hotelog API** — REST API для работы с отелями, номерами, удобствами и бронированиями.

Проект не имеет отдельного пользовательского интерфейса. Взаимодействие с приложением осуществляется через API-эндпоинты. Для просмотра и тестирования API используется Swagger UI.

Проект разработан на **Django**, **Django REST Framework** и **PostgreSQL**.

## Возможности

API позволяет:

- создавать, получать, изменять и удалять отели;
- создавать номера для конкретного отеля;
- получать список номеров выбранного отеля;
- изменять и удалять номера;
- создавать и управлять удобствами;
- присваивать номеру одно или несколько удобств;
- создавать, получать, изменять и удалять бронирования;
- проверять пересечение дат при создании и изменении бронирований;
- автоматически рассчитывать стоимость бронирования;
- сортировать номера по цене и дате добавления.

### Сортировка номеров

Для сортировки используется query-параметр `ordering`.

По цене:

```text
?ordering=price
```

По цене в обратном порядке:

```text
?ordering=-price
```

По дате добавления:

```text
?ordering=created_at
```

Сначала недавно добавленные:

```text
?ordering=-created_at
```

## Связи между сущностями

Основная структура проекта:

```text
Hotel
└── Room
    └── Booking

Room ↔ Facility
```

Один отель может содержать несколько номеров.

Каждый номер принадлежит определённому отелю.

К номеру может быть привязано несколько удобств, а одно удобство может использоваться в нескольких номерах.

Бронирование относится к конкретному номеру.

## Запуск проекта

### 1. Клонировать репозиторий

```bash
git clone <repository-url>
cd djangoFirstMR
```

### 2. Настроить переменные окружения

Создайте файл `.env` на основе `.env.example` и заполните необходимые значения.

Например, параметры подключения к PostgreSQL:

```text
DB_NAME
DB_USER
DB_PASSWORD
DB_HOST
DB_PORT
```

### 3. Запустить проект

```bash
docker compose up --build
```

При первой инициализации PostgreSQL автоматически выполняется файл:

```text
db/schema.sql
```

Он создаёт необходимые таблицы базы данных.

Данные PostgreSQL сохраняются в Docker volume, поэтому не теряются при обычном перезапуске контейнеров.

> `schema.sql` выполняется автоматически только при первоначальной инициализации пустого PostgreSQL volume.

## Как начать работу с API

Сначала необходимо создать хотя бы один отель.

В текущей версии проекта создание первого отеля при необходимости можно выполнить через Postman, отправив `POST`-запрос на:

```text
POST /hotels/
```

После создания отеля можно:

1. добавить номера этому отелю;
2. создать необходимые удобства;
3. привязать удобства к номерам;
4. создавать бронирования для существующих номеров.

Пример последовательности:

```text
Создать Hotel
↓
Создать Room
↓
Добавить Facility
↓
Привязать Facility к Room
↓
Создать Booking
```

## Основные API-операции

### Hotels

Поддерживаются операции:

- получение списка отелей;
- получение отдельного отеля;
- создание;
- полное обновление;
- частичное обновление;
- удаление.

### Rooms

Поддерживаются:

- получение номеров конкретного отеля;
- создание номера в конкретном отеле;
- получение отдельного номера;
- изменение;
- удаление;
- сортировка по цене и дате добавления.

### Facilities

Поддерживаются:

- получение списка удобств;
- создание;
- получение отдельного удобства;
- изменение;
- удаление.

### Bookings

Поддерживаются:

- получение списка бронирований;
- создание;
- получение отдельного бронирования;
- изменение;
- удаление.

При создании бронирования backend самостоятельно:

- проверяет доступность номера на выбранные даты;
- не допускает пересекающиеся активные бронирования;
- получает актуальную цену номера;
- рассчитывает количество дней;
- рассчитывает итоговую стоимость;
- фиксирует цену за ночь в бронировании;
- устанавливает начальный статус бронирования.

## Особенность пересчёта стоимости бронирования

При создании бронирования цена за ночь фиксируется в самом `Booking`.

Это позволяет сохранить историческую стоимость бронирования даже в случае, если в дальнейшем цена номера изменится.

При изменении значимых параметров существующего бронирования, например:

- номера;
- даты заселения;
- даты выселения,

стоимость бронирования пересчитывается заново на основании **актуальной цены выбранного номера**.

Например, если изначально бронирование было создано по сниженной цене, а позже пользователь изменил даты проживания, старая цена не сохраняется автоматически — используется текущая цена номера.

Такое поведение выбрано сознательно.

С одной стороны, сохранение старой скидочной цены позволило бы пользователю значительно увеличить длительность проживания и применить старую скидку к дополнительным дням.

С другой стороны, возможен другой вариант бизнес-логики, при котором первоначальная цена сохраняется для клиента.

В текущей реализации выбран первый вариант: **изменение значимых параметров бронирования приводит к перерасчёту стоимости по текущей цене номера**.
